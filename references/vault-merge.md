# Vault 增量知识合并策略

本规则用于把一次新的阅读、对话或史料输入合并进已有 Obsidian Vault，而不是每次重新生成一批孤立 Markdown。

目标：**少创建、勤合并、保留来源、关系清晰、可持续演化。**

## 1. 合并原则

### 1.1 Canonical first

每个长期知识对象只保留一个 canonical note：

- 一个人物一个主节点；
- 一个事件一个主节点；
- 一个国家/政权一个主节点；
- 一个可复用机制一个主节点；
- 一个明确比较问题一个 comparison 节点。

同义说法、别名、简称进入 `aliases`，不要另建重复文件。

### 1.2 Update before create

发现新知识时，默认顺序是：

```text
找到已有节点？
  ├─ 是 → 能合并进已有章节？
  │       ├─ 是 → UPDATE
  │       └─ 否 → 只增加关系或新章节
  └─ 否 → 是否值得长期复用？
          ├─ 是 → CREATE
          └─ 否 → 保留在阅读记录/当前回答，不建节点
```

### 1.3 Preserve user authorship

- 不覆盖无法确认来源的用户手写段落。
- 优先追加、局部修改、或更新明确的结构化章节。
- 若新判断与旧判断冲突，保留两者并新增“争议 / 修正”说明，不静默删除旧观点。
- 用户明确要求重写时除外。

## 2. 六类合并动作

对每个候选知识单位，只选最小必要动作。

### `CREATE`

仅当对象满足至少一项：

- 后续会重复出现；
- 能连接多个事件/人物；
- 是重要人物、事件、国家或制度；
- 是明确的跨案例比较主题。

### `UPDATE`

已有 canonical note，新增内容能补充：

- 身份/背景；
- 新事件；
- 新约束；
- 新证据；
- 更准确的因果解释；
- 新的待验证问题。

### `LINK`

知识本身无需新增正文，只需要表达关系，例如：

```text
[[楚悼王]] --支持--> [[吴起]]
[[吴起]] --推动--> [[吴起变法]]
```

### `PROMOTE`

某个判断最初只是事件笔记里的结论，但在多个案例反复出现时，提升为独立 `concept`。

建议门槛：

- 至少 2 个独立历史案例；或
- 用户明确要求把它作为长期分析框架。

例如：

```text
吴起变法 → 权力交接风险
商鞅变法 → 权力交接风险
```

此时可将“权力交接风险”升级为概念节点。

### `COMPARE`

只有出现明确的比较问题、且比较能揭示变量差异时才建 comparison。

不要因为两个人物同处一个时代就自动创建比较笔记。

### `DEFER`

信息价值暂时不足、来源不确定、或只是一次性疑问时：

- 保留在阅读记录；
- 放进“待继续追问”；
- 不进入 canonical 层。

## 3. 增量合并流水线

### Step A — 盘点现状

在 Vault 可访问时，先查：

1. 同名文件；
2. aliases；
3. 同类型 + 同时代 + 同国家对象；
4. 已存在的相关 MOC；
5. 已存在的相关 Canvas；
6. 当前概念是否已经存在近义节点。

优先使用 `obsidian-cli` 完成搜索与读取。

### Step B — 抽取候选知识单位

从本次阅读/对话中抽取：

- 人物；
- 事件；
- 国家/政权；
- 可复用机制；
- 明确比较问题；
- 新关系；
- 新证据；
- 未解决问题。

此阶段不要立即写文件。

### Step C — Canonical resolution

按以下顺序解析归属：

1. 文件路径/标题完全匹配；
2. aliases 匹配；
3. 类型 + 时代 + 国家能唯一确定；
4. 内容语义高度重合；
5. 仍不确定时，保守地 `DEFER` 或询问用户。

可用 `llm-wiki` 辅助发现“其实是同一个知识对象”的近义节点，但最终合并语义仍由本 Skill 决定。

### Step D — 生成 Merge Plan

写文件之前，内部形成类似：

```text
UPDATE  人物/吴起.md
  + 增加“主要约束：楚国贵族集团”
  + 增加 [[权力交接风险]]

UPDATE  事件/吴起变法.md
  + 补充“制度化程度”
  + 新关系：损害利益 → [[楚国贵族]]

CREATE  概念/权力交接风险.md
  reason: 已在吴起/商鞅两个案例重复出现

UPDATE  比较/吴起变法 vs 商鞅变法.md
  + 新增“继任者收益”比较维度

LINK    [[楚悼王]] --支持--> [[吴起]]
```

批量生成前先确定这一计划，避免边写边发散。

### Step E — 最小修改

执行顺序建议：

```text
canonical notes
    ↓
comparison / concept
    ↓
MOC
    ↓
Bases views
    ↓
Canvas
```

原因：Canvas 与 Bases 应引用已经稳定的 canonical note，而不是反过来驱动知识结构。

### Step F — 验证

至少检查：

- 是否生成重复人物/事件；
- 是否出现同义概念；
- wikilink 是否指向合理 canonical note；
- 新建概念是否真的具有复用价值；
- comparison 是否有明确比较问题；
- Canvas 是否复用了已有节点；
- 用户原有内容是否被意外覆盖。

若包内脚本可用，可运行：

```bash
python scripts/validate_vault.py /path/to/vault
python scripts/validate_canvas.py /path/to/map.canvas
```

## 4. 冲突与修正

### 新信息修正旧结论

不要直接把：

```text
吴起失败的根本原因是 X
```

静默改成 Y。

更推荐：

```markdown
## 判断演化

- 早期判断：X。
- 新增材料后：X 仍成立，但不足以单独解释结果；Y 是更关键的中介变量。
- 当前结论：X + Y，其中 Y 的解释力更强。
```

### 来源冲突

分别记录：

- 史料 A 说什么；
- 史料 B 说什么；
- 哪一项更接近《资治通鉴》叙述；
- 当前采用哪一种工作假设；
- 置信度与待查证点。

不要为了让知识图谱“整齐”而消灭不确定性。

## 5. 阅读记录与 Canonical 层分离

建议把过程性材料留在：

```text
阅读记录/
```

例如：

```text
阅读记录/2026-10-04-吴起与商鞅讨论.md
```

其中可以保留完整思考、问题、聊天摘录。

Canonical note 只吸收沉淀后的知识：

```text
人物/吴起.md
事件/吴起变法.md
概念/权力交接风险.md
比较/吴起变法 vs 商鞅变法.md
```

这样既不丢思考过程，也不会让主知识层变成聊天记录集合。

## 6. 什么时候不该更新 Canvas

以下情况只更新笔记，不动 Canvas：

- 只是补充人物出生地、官职等属性；
- 新信息没有产生新的重要关系；
- Canvas 已经很密集，而新增关系不会改变理解；
- 用户只要求整理文字笔记。

只有当新知识改变“结构关系”时才更新 Canvas。
